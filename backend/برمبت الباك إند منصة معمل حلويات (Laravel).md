# برمبت الباك إند: منصة معمل حلويات (Laravel)

> انسخ هذا البرمبت كاملًا للمساعد البرمجي (Claude Code / Cursor). نفّذ على مراحل، وبعد كل مرحلة شغّل الاختبارات وأخبرني بالملخص قبل الانتقال للتالية.

---

## 0) الدور والقواعد العامة

أنت مهندس Laravel خبير. ابنِ الباك إند الكامل لمنصة معمل حلويات: **REST API لتطبيق Flutter + لوحة تحكم ويب**.

- اللغة: PHP 8.3 و Laravel 11، قاعدة MySQL 8، Redis للطوابير والكاش.
- كل الأسماء البرمجية (جداول، أعمدة، كلاسات، مسارات) بالإنجليزية. كل النصوص الظاهرة للمستخدم بالعربية عبر ملفات `lang/ar`، والواجهة RTL.
- العملة الافتراضية: دينار ليبي (LYD) وتُقرأ من الإعدادات. المنطقة الزمنية الافتراضية `Africa/Tripoli`.
- المعمارية: `Controller → FormRequest → Action/Service → Model`. لا منطق أعمال داخل الـ Controllers. استخدم API Resources للردود، و Policies للصلاحيات، و Enums للحالات.
- كل رد API بصيغة موحدة: `{ success, message, data, errors }` مع رسائل أخطاء عربية.
- اكتب Migrations و Factories و Seeders و Feature Tests (Pest) لكل وحدة.
- المبالغ تُخزَّن كـ `decimal(12,2)`، والتواريخ UTC وتُعرض بتوقيت المعمل.
- أي عملية مالية أو إنشاء طلب داخل `DB::transaction` مع قفل مناسب (`lockForUpdate`) لمنع تجاوز السعة.

## 2) المستخدمون والصلاحيات (لوحة التحكم)

- جدول `users` للموظفين، منفصل عن `customers` (عملاء التطبيق) بـ guard مختلف.
- الأدوار: مدير عام، مدير مبيعات، محاسب، مشرف محتوى، موظف طلبات، مشرف مشتريات.
- صلاحيات لكل وحدة بالصيغة `module.action` (view, create, update, delete, export). مثال: `orders.update`.
- **قيود لكل مستخدم:** `is_active`، الوحدات المسموحة، صلاحيات إضافية أو مسحوبة فردية فوق الدور، وتاريخ انتهاء حساب اختياري.
- سجل نشاط لكل عملية (من فعل ماذا ومتى وعلى أي سجل).
- إدارة العملاء: حظر/فك حظر، عرض الطلبات، ملاحظات داخلية.
- المدير العام فقط يدير المستخدمين والأدوار والإعدادات الحساسة (ملف الإشعارات ومفاتيح الذكاء الاصطناعي).

## 3) الكتالوج

**الأقسام `categories`:** الاسم، الصورة، الترتيب، الحالة، `parent_id` اختياري (حلو، حار، مأكولات، عصائر...).

**المنتجات `products`:** الاسم، الوصف، السعر، القسم، `is_available`، `lead_time_hours` (أقل مدة تجهيز)، `daily_limit` اختياري، `serves_min` و `serves_max` (يكفي كم شخص)، المكونات، تنبيهات الحساسية، صور متعددة.

**الوسوم `tags`:** مناسبات (زواج، عيد ميلاد، تخرج، عزاء، عزومة) وصفات. علاقة many-to-many مع المنتجات. مهمة جدًا للذكاء الاصطناعي.

**الأكثر طلبًا:** يُحسب تلقائيًا من `order_items` للطلبات المكتملة خلال آخر 30 يومًا، ويُخزَّن في الكاش ويُحدَّث بجدولة.

**البانرات `banners`:** صورة، نوع الرابط (product / category / collection / coupon / none) مع المعرّف، ترتيب، `starts_at` و `ends_at`، حالة.

**الكلكشنز `collections`:** باقة بسعر ثابت. جدول `collection_items` فيه المنتج والكمية. `lead_time` الباقة = أكبر قيمة بين منتجاتها. صور وسعر وحالة وتواريخ عرض.

**عروض التخفيض:** `discount_price` اختياري على المنتج مع `discount_starts_at/ends_at`، وتظهر في قسم العروض.

## 4) الكوبونات

`coupons`: الكود، النوع (نسبة / مبلغ ثابت)، القيمة، أقصى خصم للنسبة، الحد الأدنى للطلب، حد استخدام عام وحد لكل عميل، البداية والنهاية، نطاق التطبيق (الكل / أقسام / منتجات محددة)، الحالة. و`coupon_usages`.

التحقق في Service واحدة `CouponService::validate($code, $cart, $customer)` تُستخدم في التطبيق وعند إنشاء الطلب، وتعيد سبب الرفض بالعربية.

## 5) إعدادات المعمل والمواعيد (⭐ أساس النظام)

الجداول: `business_hours` (day\_of\_week, open\_at, close\_at, is\_closed)، `closed_dates` (date, reason)، `delivery_slots` (start\_time, end\_time, max\_orders, type: pickup/delivery/both)، وجدول `settings` (key/value) يشمل: `min_lead_hours`، `max_advance_days`، `daily_capacity`، `delivery_fee`، `cancel_policy_hours`، `cancel_policy_refund_percent`.

**الخدمة `FulfillmentService`:**

1. `earliestDateTime($cart)` = الآن + أكبر `lead_time_hours` بين عناصر السلة (وأعلى من الحد الأدنى العام).
2. `availableDates($cart, $type)` تستبعد: الإجازات، الأيام المغلقة، ما بعد `max_advance_days`، الأيام التي امتلأت سعتها، وأيام تجاوز فيها منتج `daily_limit`.
3. `availableSlots($date, $type, $cart)` تعيد الفترات داخل ساعات العمل مع المتبقي لكل فترة، وتستبعد الممتلئ وما قبل أقرب موعد.
4. `assertValid(...)` تُستدعى داخل transaction عند إنشاء الطلب وتفشل بخطأ 422 واضح إذا لم يعد الموعد متاحًا.

## 6) السلة والطلبات

الطلب لا يُؤكَّد بالدفع مباشرة، بل **يمرّ بمراجعة الأدمن أولًا**. هذا هو المسار الإلزامي:

### أ. رحلة الطلب

1. **السلة:** يضيف العميل الأصناف بنفسه أو عبر المساعد الذكي (نفس API السلة، بالكمية).
2. **بيانات التسليم:** استلام من المعمل أو توصيل، ثم اليوم والساعة. للتوصيل: وصف الموقع (+ lat/lng اختياري). وإن كان المستلم غير العميل: اسمه ورقمه (`recipient_is_self=false` ← `recipient_name` و`recipient_phone` مطلوبان).
3. **إرسال الطلب (بدون دفع):** الحالة `pending_review`. يتحقق النظام مبدئيًا من الموعد (`FulfillmentService`) ويحجز السعة **مؤقتًا** لهذا الموعد.
4. **مراجعة الأدمن:** يرى الطلب مع مؤشر تلقائي ✅/⚠️ (مدة التجهيز، السعة، ساعات العمل، الإجازات)، ثم يختار: **قبول**، أو **رفض** بسبب من قائمة جاهزة (ضيق الوقت، اكتمال السعة، منتج غير متاح، غير ذلك) مع ملاحظة اختيارية، أو **اقتراح موعد بديل**.
5. **عند القبول:** الحالة `awaiting_payment`، ويصل العميل إشعار «تمت الموافقة، يرجى الدفع» فيه المبلغ المطلوب. يختار العميل **دفعة أولية (25% أو 50%) أو كاملة (100%)** (الحد الأدنى `min_advance_percent` من الإعدادات)، وله مهلة `payment_due_at` (افتراضيًا 24 ساعة، قابلة للضبط).
6. **عند الرفض:** الحالة `rejected` مع السبب، ويُحرَّر الحجز ويصل العميل إشعار بالسبب.
7. **انتهاء المهلة دون دفع:** الحالة `expired`، ويُحرَّر الحجز تلقائيًا ويُشعَر العميل.
8. **بعد تأكيد الدفعة** (تلقائيًا من البوابة لاحقًا، أو يدويًا من الموظف الآن): الحالة `confirmed` وتُحسم السعة نهائيًا، ثم يكمل المسار.

### ب. الحالات (State machine)

`pending_review → awaiting_payment → confirmed → preparing → ready → out_for_delivery → completed`، وكذلك `rejected` و`expired` و`cancelled`. الانتقالات المسموحة فقط، وكل انتقال يُسجَّل في `order_status_logs` (من، متى، السبب) ويطلق Event يرسل إشعارًا للعميل.

### ج. حقول الطلب

- `number`، `customer_id`، `delivery_type` (pickup/delivery)، `fulfillment_date`، `fulfillment_time`، `address_text`، `lat`، `lng`، `delivery_fee`.
- `recipient_is_self`، `recipient_name`، `recipient_phone`.
- `subtotal`، `discount`، `coupon_id`، `total`، `payment_plan` (25/50/100، يُحدَّد بعد القبول)، `paid_amount`، `remaining_amount`، `payment_status` (`unpaid / partial / paid`)، `payment_due_at`.
- `status`، `reviewed_by`، `reviewed_at`، `rejection_reason_id`، `admin_note`، `customer_note`.
- جدول `rejection_reasons` (نصوص جاهزة قابلة للإدارة).

### د. قواعد أخرى

- عند الإرسال تُنسخ الأسعار والأسماء داخل `order_items` (snapshot).
- الضيف يُطلب منه التسجيل عند إرسال الطلب (401 برمز واضح)، وتُدمج سلته بعد الدخول.
- الإلغاء من العميل يخضع لـ `cancel_policy_hours` ونسبة الاسترداد من الدفعة المقدمة.
- يتحقق الباك إند من الموعد مرة أخرى لحظة **القبول** داخل transaction مع `lockForUpdate`، حتى لا يُقبل طلب تجاوز السعة.

### هـ. لوحة التحكم

- شاشة **«بانتظار المراجعة»** بعدّاد (badge) وأولوية حسب أقرب موعد، وأزرار قبول/رفض/موعد بديل.
- **خط زمني (Timeline) لكل طلب** يعرض كل ما حدث: الإرسال، المراجعة وصاحبها، الإشعارات المرسلة، الدفعات (المبلغ، الطريقة، من سجّلها)، تغيّر الحالات.
- فلاتر: اليوم، غدًا، الأسبوع، حسب الحالة، وطلبات عليها **مبلغ متبقٍ**؛ مع عرض تقويم، وفاتورة PDF، **وشاشة تحضير المطبخ** (إجمالي كميات كل صنف لتاريخ معيّن، للطلبات المؤكدة فقط).

## 7) الدفع (طبقة مجردة Stand-by)

```php
interface PaymentGateway {
  public function initiate(Payment $payment): PaymentSession;
  public function verifyWebhook(Request $request): PaymentResult;
}
```

- المزوّدات: `ManualGateway` (الافتراضي: الموظف يسجّل الدفعة يدويًا من اللوحة) و`FakeGateway` (للتطوير، يؤكد تلقائيًا). يُختار عبر `PAYMENT_DRIVER` في `.env` وينشئه `PaymentManager`، ولا منطق خاص ببوابة داخل بقية الكود.
- **لا يُسمح بالدفع إلا بعد القبول** (الحالة `awaiting_payment`). `POST /orders/{id}/pay` يستقبل `payment_plan` (25/50/100) ويُنشئ دفعة `advance` بالمبلغ `total × plan / 100`.
- `payments`: `order_id`، `type` (advance / remainder)، `method` (online / cash / transfer / card\_on\_delivery)، `amount`، `status`، `reference`، `paid_at`، `recorded_by`.
- عند اكتمال الدفعة الأولى: `payment_status = partial` (أو `paid` إن كانت 100%) ويتحول الطلب إلى `confirmed`، ويُحسب `remaining_amount`.
- **المتبقي يُحصَّل عند الاستلام:** الموظف يسجّل دفعة `remainder` من اللوحة، فيصبح `payment_status = paid` ولا يُكتمل الطلب (`completed`) وعليه مبلغ متبقٍ إلا بتأكيد صريح من الموظف.
- كل دفعة تظهر في الخط الزمني للطلب وفي سجل النشاط، وتدخل في الإيرادات.
- مسار `POST /payments/webhook` جاهز بتحقق توقيع وعدم تكرار التأثير (idempotency) لاستخدامه مع أي بوابة لاحقًا.

## 9) إدارة الإشعارات (FCM) ⭐

### أ. الجداول

`device_tokens` (customer\_id، token، platform، last\_used\_at)، `notifications` (الحملات: عنوان، نص، صورة، شريحة مستهدفة، `scheduled_at`، حالة)، `notification_logs` (لكل إرسال: النتيجة والخطأ)، وجدول `integration_settings` للاعتمادات.

### ب. رفع ملف الاعتماد (Private Key)

صفحة في اللوحة: **الإعدادات ← الإشعارات ← اتصال Firebase**، للمدير العام فقط (صلاحية `settings.firebase`).

1. حقل رفع لملف **Service Account JSON** من Firebase Console.
2. التحقق عند الرفع: JSON صالح، يحتوي `type=service_account` و`project_id` و`private_key` و`client_email`. ارفض أي ملف غير ذلك.
3. التخزين: في قرص **خاص** `storage/app/private/firebase/` بعيدًا عن `public`، باسم عشوائي، وصلاحيات ملف 600. **ممنوع** إظهار المحتوى أو المسار في أي واجهة أو API أو log. تُعرض فقط: `project_id` و`client_email` وتاريخ الرفع، والمفتاح مخفي.
4. أضف المجلد إلى `.gitignore`. ويمكن بديلًا قراءة المسار من `FIREBASE_CREDENTIALS` في `.env`؛ والأولوية لما رُفع من اللوحة.
5. الاستبدال والحذف: رفع ملف جديد يحذف القديم بأمان، وكل عملية تُسجَّل في activity log.
6. `FirebaseCredentialsProvider` تحلّ المسار وتبني `kreait Factory` عند الحاجة.

### ج. زر «اختبار الاتصال»

يشغّل `FirebaseConnectionTester` ويعرض نتيجة كل خطوة (✅ / ❌ مع سبب عربي):

1. وجود الملف وقابلية قراءته.
2. صحة بنية JSON والحقول المطلوبة.
3. الحصول على Access Token من Google (يثبت صلاحية المفتاح).
4. تطابق `project_id` مع المشروع المضبوط.
5. **إرسال تجريبي بوضع `validate_only`** (`$messaging->send($message, true)`) فلا يصل أي إشعار فعلي، ويثبت أن الصلاحيات كاملة.
6. اختياري: حقل لإدخال token جهاز لإرسال إشعار حقيقي «تجربة الاتصال».

تُحفظ آخر نتيجة (`last_tested_at`، `last_test_status`، `last_error`) وتظهر كشارة حالة (متصل / فشل / لم يُختبر). كذلك أمر `php artisan firebase:test`.

### د. الإرسال

- حملات: للجميع أو لشريحة (عملاء لديهم طلبات، لم يطلبوا منذ 30 يومًا...) مع جدولة وإرسال عبر الطوابير بدفعات (500 token)، وحذف التوكنات غير الصالحة تلقائيًا.
- **إشعارات دورة الطلب (تلقائية، لكل منها قالب نص عربي قابل للتعديل من اللوحة):**
  1. إرسال طلب جديد ← إشعار للأدمن/الموظفين (داخل اللوحة + FCM للموظفين اختياريًا).
  2. قبول الطلب ← للعميل: «تمت الموافقة، يرجى الدفع» مع المبلغ والمهلة.
  3. رفض الطلب ← للعميل مع السبب (مثل ضيق الوقت).
  4. تذكير قبل انتهاء مهلة الدفع (مثلًا قبل 3 ساعات)، ثم إشعار الانتهاء.
  5. تأكيد استلام الدفعة ← للعميل، ويذكر المتبقي إن وُجد.
  6. تغيّر حالة الطلب (تحضير، جاهز، خرج للتوصيل، مكتمل).
  7. **تذكير قبل الموعد بيوم** لكل طلب مؤكد.
  8. **صباح يوم الاستلام/التوصيل (وقت قابل للضبط `remaining_reminder_time`، افتراضيًا 08:00):** إذا كان على الطلب مبلغ متبقٍ يصل العميل إشعار «لا تنسَ دفع باقي المبلغ (X د.ل) عند الاستلام».
  9. صباح يوم التسليم ← ملخص للمعمل: طلبات اليوم والمتبقي تحصيله.
- تُنفَّذ التذكيرات بأمر مجدول (`schedule:work`) مع منع التكرار (idempotency) عبر `notification_logs`.
- مركز إشعارات داخل التطبيق: `GET /notifications` مع مقروء/غير مقروء، و`POST /devices` لتسجيل token الجهاز وحذفه عند الخروج.
- كل إشعار يُسجَّل في اللوحة (المستلم، النوع، النتيجة، الخطأ) ويظهر ضمن الخط الزمني للطلب، مع إعادة محاولة الفاشل.

## 10) الذكاء الاصطناعي (مساعد الحلويات)

المزوّد (Claude أو غيره) والمفتاح والبرمبت كلها تُدار من لوحة التحكم، بدون لمس الكود أو ملف `.env`.

### أ. مزوّد قابل للتبديل

```php
interface AiProvider {
  public function chat(array $messages, AiOptions $options): AiResponse;
  public function test(): AiTestResult;
}
```

- يُنفَّذ بسائقين فقط، ويُختار من الإعدادات عبر `AiManager`:
  1. `AnthropicProvider` لـ Claude.
  2. `OpenAiCompatibleProvider` (يعمل بـ `base_url` + `api_key` + `model`)، ويغطي OpenAI وGroq وOpenRouter وGoogle Gemini (عبر نقطة التوافق مع OpenAI) وOllama المحلي.
- أمثلة جاهزة تظهر كقوالب في قائمة المزوّد، فيعبّأ `base_url` والنموذج الافتراضي تلقائيًا ويُعدَّلان يدويًا. القوالب المجانية المقترحة: **Google Gemini** (طبقة مجانية من AI Studio)، **Groq** (نماذج Llama بطبقة مجانية)، **OpenRouter** (نماذج بلاحقة `:free`)، و**Ollama** (مجاني بالكامل على سيرفرك، ويحتاج جهازًا بقدرة كافية). الحدود والأسعار تتغير، لذا تُراجع من موقع كل مزوّد قبل الاعتماد.
- مزوّد احتياطي اختياري (Fallback): إذا فشل الأساسي أو تجاوز حدّه المجاني، يُجرَّب الثاني تلقائيًا.

### ب. إعدادات الذكاء الاصطناعي في اللوحة

صفحة **الإعدادات ← الذكاء الاصطناعي** للمدير العام فقط (صلاحية `settings.ai`):

- تفعيل/إيقاف البوت، واختيار المزوّد، و`base_url`، واسم النموذج، و`temperature`، و`max_tokens`.
- **حقل مفتاح API:** يُحفظ مشفّرًا (`encrypted` cast أو `Crypt::encryptString`) في جدول `ai_settings`، ويُخفى من كل الردود (`$hidden`). في الواجهة يظهر مقنّعًا (`sk-••••1234`) مع زر «تغيير المفتاح»، ولا يُعاد المفتاح الكامل أبدًا. ولا يُكتب في logs أو activity log (يُسجَّل فقط أنه تغيّر ومن غيّره).
- **محرّر البرمبت (System Prompt):** حقل نص كبير قابل للتعديل مع قالب افتراضي، ومتغيّرات يستبدلها النظام وقت التشغيل مثل `{{products}}` و`{{collections}}` و`{{today}}` و`{{lead_time_rules}}`. زر «استرجاع الافتراضي».
- **سجل نسخ البرمبت** `ai_prompt_versions` (النص، من عدّل، متى) مع إمكانية الرجوع لنسخة سابقة.
- حد الرسائل اليومي لكل مستخدم، وقائمة المنتجات المسموح اقتراحها (`ai_suggestable`).
- **زر «اختبار الاتصال»:** يرسل رسالة قصيرة للمزوّد المختار ويعرض: ✅/❌ ، زمن الاستجابة، اسم النموذج، وسبب الفشل بالعربية (مفتاح خاطئ، حد مجاني منتهٍ، نموذج غير موجود، رابط غير صحيح). يُحفظ آخر نتيجة (`last_tested_at`, `last_test_status`, `last_error`) كشارة حالة.
- لا يُفعَّل البوت للعملاء إلا بعد نجاح الاختبار مرة واحدة على الأقل.

### ج. التدفق في `AssistantService`

1. استقبل الرسالة وتحقق من حد الاستخدام.
2. اجلب المنتجات والباقات المتاحة (الاسم، السعر، الوسوم، حجم الحصة، `lead_time`) من القاعدة، مع كاش قصير، وحقنها في البرمبت.
3. أرسلها مع آخر الرسائل عبر `AiManager`، واطلب **ردًا بصيغة JSON فقط**: `{ "message": "...", "suggestions": [{ "type": "product|collection", "id": 1, "quantity": 3, "reason": "..." }] }`.
4. **تحقق صارم من الرد:** النماذج المجانية أقل التزامًا بالصيغة، فاستخرج JSON حتى لو أحاطه نص أو علامات \`\`\`، وإذا فشل التحليل أعد المحاولة مرة واحدة بتنبيه، وإلا أعد ردًا نصيًا فقط بدون اقتراحات.
5. تجاهل أي id غير موجود أو غير متاح، وأعد حساب الأسعار من القاعدة (لا تثق بأرقام النموذج).
6. علّم البوت أن يسأل عن **عدد الأشخاص ونوع المناسبة وتاريخها**، ولا يقترح إلا ما يمكن تجهيزه قبل ذلك التاريخ.
7. احفظ المحادثة في `ai_conversations` و`ai_messages` (الدور، النص، `suggested_items`، المزوّد والنموذج المستخدمان، زمن الاستجابة).

### د. المسارات

- التطبيق: `POST /ai/chat` و`GET /ai/conversations`. زر «أضف للسلة» يستخدم API السلة نفسه.
- اللوحة: عرض المحادثات وما اقترحه البوت، إحصاءات الاستخدام والأخطاء، وزر تجربة البوت.
- أخطاء المزوّد (حد منتهٍ، مهلة، 5xx) تُعالج برسالة لطيفة للعميل وتُسجَّل في اللوحة، ولا تُسقط التطبيق.

## 12) الأمان والجودة

- FormRequests لكل مدخل، وPolicies لكل مورد، وعزل بيانات العميل (لا يرى إلا طلباته).
- لا أسرار في الكود أو الـ logs، و`.env.example` كامل.
- Indexes على: `fulfillment_date`، `status`، `customer_id`، `category_id`.
- Seeder يضيف: الأدوار والصلاحيات، مدير عام، ساعات عمل افتراضية، أقسام ومنتجات تجريبية بوسوم، وكوبون تجريبي.
- توثيق API عبر Scribe أو OpenAPI، ومجموعة Postman.
- `README` عربي يشرح التشغيل، الطوابير، الجدولة (`schedule:work`)، وإعداد Firebase.
